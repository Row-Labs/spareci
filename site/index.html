Free macOS CI on the Mac on your desk.

spareci runs your GitHub Actions jobs on a machine you already own. One command to set up, one line changed in your workflow. When the machine is off, asleep or busy, jobs run on GitHub-hosted runners as before.

Install spareci What would I save?

GitHub bills $0.062 a minute for macOS and $0.006 for Linux. That's about 10x. A Mac mini you already paid for bills nothing.

How it works

  1. 1

    See what it would save

    spareci estimate

    Reads the last 30 days of runs through the GitHub API, prices each job the way GitHub bills it, and shows which minutes this machine could take. Changes nothing.

  2. 2

    Opt jobs in

    spareci init

    Lists your workflow jobs, recommends the ones this machine can run (same OS and CPU), rewrites only their runs-on lines and opens a pull request.

  3. 3

    Take jobs

    spareci install

    Runs spareci in the background, now and at every login. Each job gets a fresh, single-use copy of GitHub's official runner. Logs, checks and artifacts look the same as on hosted runners.

  • No inbound connections. spareci polls GitHub, so it works behind NAT, on Wi-Fi, on a laptop.
  • Local cache. actions/cache and every setup-* action save to this machine's disk. Saving a 1 GB Go build cache takes seconds, not a minute.
  • Laptop mode. --only-on-ac, --idle 10m and --hours 18:00-08:00 keep jobs off the machine while you're using it.
  • No new infrastructure. No Kubernetes, no Terraform, no cloud account, no webhook server.

CI never waits on a sleeping laptop

Your jobs only go to your machine while spareci says it's there. Every other time, they run where they always did.

You stop it
^C, spareci uninstall or laptop mode pausing: new jobs go to GitHub right away, running jobs finish, and jobs still queued here are sent to GitHub-hosted runners.
It's busy
A job that waits here longer than --max-wait (10 minutes by default) is sent to GitHub-hosted runners.
It dies
Crash, power cut, lid closed. spareci install restarts a crashed process within 10 seconds. If the whole machine is gone, a small watchdog workflow notices the missing heartbeat and re-runs stranded jobs on GitHub, usually within 15 to 20 minutes. It's skipped, and not billed, while spareci is healthy.

    Security, honestly

    spareci is early. Today every job runs directly on the host, as your user.

    Each repo's jobs get their own home directory and a cleaned environment, so they don't see your shell's tokens, your ~/.gitconfig or the tools in your home. That keeps jobs out of your personal tool state, not out of your account: a job can still read any file your user can, your SSH keys included. It's the same trust you give a workflow when you run its commands yourself.

    • Use it with private repos whose workflows and contributors you trust.
    • Never with public repos. A fork's pull request could run code on your machine.

    Per-job isolation, VMs on macOS and containers on Linux, is the next major milestone. Public-repo support waits for it. The design is in docs/isolation.md.

    Install

    macOS or Linux, arm64 or x64. You'll need the GitHub CLI logged in and admin rights on the repo, since registering runners needs them.

    Homebrew

    brew trust row-labs/spareci
brew install row-labs/spareci/spareci

    Prebuilt binary

    curl -fsSL https://github.com/Row-Labs/spareci/releases/latest/download/spareci_darwin_arm64.tar.gz | tar xz spareci
sudo mv spareci /usr/local/bin/

    Swap darwin for linux and arm64 for amd64 to match your machine.

    Go

    go install github.com/Row-Labs/spareci/cmd/spareci@latest

    Then, in your repo

    spareci estimate   # what your minutes cost, and what this machine could take
spareci init       # opt jobs in; opens a pull request
spareci up         # take jobs until ^C (or spareci install to keep it running)

    Read the README for laptop mode, the watchdog workflow and what a job can see.
